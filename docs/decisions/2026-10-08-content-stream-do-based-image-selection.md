# 描画画像の特定は content stream の Do 演算子で行い、結合順は描画位置で決める

## 背景
初版はページの /Resources → /XObject 辞書に登録された JPEG を全て結合し、順序は XObject 名の
文字列順としていた。画像→PDF変換ツールの出力(例: コマツ WA200-1 の54ページPDF)では全ページが
1つの /Resources を共有し、辞書に全ページ分の画像が並ぶため、各ページで54枚全部を結合してしまった。

## 選択肢
- A: /XObject 辞書の列挙を続け、ページ番号と名前の対応をヒューリスティックで推定する
- B: content stream を走査し、`/Name Do` で実際に描画された XObject だけを使う。順序は出現順
- C: B に加えて q/Q/cm で CTM を追跡し、描画位置(上端 y 降順、左端 x 昇順)で結合順を決める

## 決定
C を採用。Do が1つも見つからない場合のみ、従来の全列挙(名前は自然順)にフォールバックする。

## 理由
- /Resources は「参照してよい素材の辞書」であり「描かれているもの」ではない。描画の有無は
  content stream でしか判定できず、A は構造の仮定に依存して脆い
- 分割画像の上下関係は描画命令の出現順と一致する保証がない。CTM から位置を求めれば
  名前順・出現順のどちらにも依存しない
- 走査に必要なのは q/Q/cm/Do の4演算子と、文字列・辞書・インライン画像の読み飛ばしだけで、
  Pure Go・標準ライブラリのみという方針を崩さずに実装できる

## 備考
- Form XObject(/Subtype /Form)内部からの Do は追っていない。必要になれば Form の
  /Matrix と /Resources を使って再帰走査する
- /Resources はページに無ければ /Parent を遡って継承元から取得する(同時に対応)
